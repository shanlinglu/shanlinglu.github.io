这份教程用「拾光旅路」做例子。我们从“想做一个有毕业相册感觉的照片墙”出发，逐步拆出页面、照片存储、切换交互、加载速度和上线检查。学完后，你会知道从哪一步动手，也能判断每一步为什么存在。

## 先建立一张地图

网页开发可以看成一条交付路径：

**用户要完成什么 → 数据从哪里来 → 页面怎么展示 → 操作如何改变页面 → 怎么验证 → 怎么发布。**

例如，拾光旅路的使用流程是：访客进入页面，看见一张照片和周围的回忆，滑动或等待自动播放来切换照片。宿舍成员把新照片提交到 GitHub 后，网站重新构建，大家再打开网页就能看到更新。

先把目标写成可以检查的结果：

- 页面从主导航可以打开，手机和电脑都能铺满展示区域。
- 相册每次打开会随机选一张照片，之后可手动切换，也可自动播放。
- 新照片对团队成员共享，部署后所有访客看到相同内容。
- 网络较慢时先看到当前照片，其他照片稍后加载。个别图片出错时仍可继续浏览。

这些结果会决定技术结构。早一点明确“团队共享”很重要，因为它影响数据应该放在哪里，也影响上传按钮究竟要做什么。

## 看懂静态网站的数据流

山泠庐使用 Astro 生成静态网页，并部署到 GitHub Pages。拾光旅路的数据流大致是：

```text
成员提交原始照片到 GitHub
        ↓
GitHub Actions 安装依赖并构建网站
        ↓
Sharp 生成适合网页展示的 WebP 图片
        ↓
GitHub Pages 发布静态页面和展示图
        ↓
访客的浏览器加载页面与照片
```

这个站点没有一个接收网页上传请求的服务器。页面上的“添加照片”按钮会打开 GitHub 的文件上传入口，GitHub 负责登录、权限和提交。团队成员需要有仓库写入权限，提交并部署完成后，照片才会出现在相册里。

如果要求访客留在网页内，选完照片就立刻上传并让其他人实时看到，就需要一个有身份验证的后端或对象存储服务。访问令牌不能写进浏览器代码，因为所有访客都能查看网页代码。先选择数据的来源，再设计界面，会少走很多弯路。

## 从零打开项目

先安装 Git 和 Node.js。这个项目的工作流使用 Node.js 24。然后在 PowerShell 中运行：

```powershell
git clone https://github.com/shanlinglu/shanlinglu.github.io.git
Set-Location shanlinglu.github.io
git status --short
Get-ChildItem src, works -Recurse -File | Select-Object -ExpandProperty FullName
Get-Content package.json
npm ci
npm run dev
```

这些命令各自负责一件事。`git clone` 下载项目，`git status` 看工作区有没有已有改动，`Get-ChildItem` 让你先认识文件，`Get-Content package.json` 查看技术栈和脚本，`npm ci` 按锁文件安装准确的依赖，`npm run dev` 启动本地预览。终端会打印一个地址，复制到浏览器打开。

项目已有路由、布局、图标库、构建和发布流程。开始开发前，先找一个功能相近的页面，理解它怎么接入，再沿用它的做法。新功能通常不需要先换框架或增加依赖。

## 把功能拆到合适的文件

前端页面可以按职责拆成几层。每一层只处理自己负责的事情：

- **页面结构** 放在 `src/pages/journey.astro`，描述有哪些按钮、照片和状态。
- **样式** 放在 `src/styles/journey.css`，决定全屏布局、照片层次和移动端尺寸。
- **交互** 放在 `src/lib/journey-album.ts`，管理当前照片、切换、拖动和自动播放。
- **照片清单** 由 `src/lib/journey-photos.ts` 在构建时读取，生成页面需要的数据。
- **原始文件** 保存在 `public/journey-photos/`，团队成员从这里共享照片。
- **图片处理** 由 `scripts/optimize-journey-photos.mjs` 在构建时压缩照片，生成 WebP 展示图。

不用一开始就把所有代码抽象成很多模块。可以先让一个最小页面正常显示，再按照职责拆开数据读取、交互和视觉样式。拆分的目的在于让下一次修改能迅速找到对应位置。

## 按垂直步骤实现

所谓垂直步骤，就是每一步都从用户能看见的结果出发，做到可以运行和检查。

1. **先搭出页面。** 创建 `/journey/` 路由，放一个固定的示例照片，确认页面比例、导航入口和移动端布局。
2. **接入真实数据。** 把团队照片放进仓库目录，构建时扫描文件，生成照片清单，再让页面根据清单展示内容。
3. **加入交互。** 先实现上一张、下一张和滑动，再加入键盘操作与自动播放。把“当前是第几张”当成明确状态，由所有切换入口调用同一段更新逻辑。
4. **补齐失败路径。** 照片加载失败时显示占位内容。焦点图加载慢时设置等待上限，之后仍显示舞台。隐藏照片时不要把焦点留在用户无法操作的按钮上。
5. **最后优化资源。** 先确认照片能正确展示，再加入图片压缩和分批加载。这样每次遇到问题时，变化范围更清楚。

每完成一步都在浏览器里实际点一遍。只检查代码能否编译，无法证明鼠标、键盘和手机触摸能正常工作。

## 处理“只有背景”的加载问题

遇到网页只显示背景，先在浏览器开发者工具的 Network 面板里筛选 `Img`，观察照片请求是否发出、响应是否为 `200`、文件大小是多少。再看 Console 有没有 JavaScript 错误。这样可以区分图片链接错误、图片传输过慢、脚本没运行和 CSS 把照片藏起来。

拾光旅路上线后发现，主站的 21 张原始照片合计约 69 MB，最大的一张约 7.2 MB。电脑较慢或网络较差时，浏览器要处理很多大图。我们在构建期间用 Sharp 将图片转换为 WebP，把最长边限制为 2200 像素，再让浏览器优先请求焦点图。周围的照片在焦点图显示后才开始加载。21 张展示图合计约 7.6 MB，比原图少约 89%。

这次优化分成两部分：

- **减少每张图的成本。** 在构建阶段压缩图片，控制尺寸，浏览器就不必下载相机原图。
- **安排加载顺序。** 先请求当前照片。它显示或等待超时后，再请求周围照片。用户第一眼不必等整组图片全部下载完。

性能问题要从实际请求和数据体积查起。改 CSS 可能会移动或隐藏照片，但不会让几兆字节的文件变小。

## 让“能运行”变成“可交付”

本地开发时先检查几个核心流程：

- 鼠标、键盘方向键和手机滑动都能切换照片。
- 自动播放每 5 秒切换，手动暂停后不再自动变化。
- 图片加载失败后显示占位图，仍能继续看下一张。
- 窄屏没有横向溢出，按钮仍可触摸。
- 慢速网络下焦点照片能先出现，关闭 JavaScript 时也有可读的静态内容。

修改后运行生产构建：

```powershell
npm run build
npm run preview
```

`npm run dev` 适合边写边看。`npm run build` 会生成真正要部署的静态文件。`npm run preview` 用本地浏览器检查这些构建产物。两种运行方式的路径和资源处理可能不同，所以发布前要看构建结果。

打开开发者工具的 Network 面板，启用慢速网络模拟并禁用缓存，再重新加载页面。确认当前焦点图请求成功，周围照片在它之后加载，展示图返回 `image/webp`。在开发者工具的设备模式中再检查手机尺寸。

## 从本地修改到线上发布

先为一个明确的小任务创建分支，再检查最终改动：

```powershell
git switch -c add-frontend-guide
git diff --check
npm run build
git status --short
git diff
```

确认改动和构建结果后，再提交并推送：

```powershell
git add works/frontend-from-zero/index.md
git commit -m "添加前端入门教程"
git push -u origin add-frontend-guide
```

随后在 GitHub 上创建 Pull Request。项目的 Actions 会构建网站。先检查构建结果和预览，再合并到 `main`。Pages 部署成功后，访问作品集卡片和文章地址，确认线上内容正常。

这段流程让每次发布都有可检查的差异、构建结果和回退记录。直接推送到正式分支时，也要确保本地构建和线上部署状态都成功。

## 以后做新功能时

开始前，先回答这几个问题：

1. 用户会怎么完成这件事？在哪一步需要提示或失败回退？
2. 页面所需的数据在哪里产生、由谁修改、谁能看到？
3. 这个项目是静态构建还是运行中的服务？要不要后端权限？
4. 改动分别属于页面结构、样式、交互、数据还是构建流程？
5. 用哪些具体操作、屏幕尺寸和慢网情况证明它能用？

按顺序把答案变成一个最小可运行版本，再逐步补全边界情况。前端开发的核心是管理数据、状态、用户操作和交付过程。框架与组件是落实这些决定的工具。
